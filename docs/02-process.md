# 二、项目创作与制作流程

## 2.1 总流程

```
① 创意与剧本  →  ② 平台一键直出  →  ③ 素材回收  →  ④ 本地后期  →  ⑤ 交付
   （本地·0积分）      （Canvas API）      （签名下载）      （ffmpeg·0积分）    （仓库）
```

一个反直觉的设计：**把最贵的事一次性做完，把最便宜的事反复打磨。**
生成视频（付费）只跑一遍，绝不重抽；后期修整（免费）在本地想改几遍改几遍。

## 2.2 阶段一：创意与剧本（本地完成，0 积分）

在调用任何算力之前，先在本地把三件事定死：

1. **植入逻辑**：确定"商品即麦高芬"的设计原点，确保商品抽掉剧情即不成立（见 `01-brief.md`）
2. **产品资料**：梳理吉普号 503 的真实卖点——三山拼配（易武 / 勐海 / 临沧）、米汤感、木质香、无堆味、十二年陈化、太极双鱼标志、龙珠形态
3. **剧本成文**：写成完整剧本（含集数、场景、动作、旁白、对白），一次性提交给平台的 `quick-start` 接口

这一步是**成本战的胜负手**。平台 LLM 在拿到完整剧本时只做忠实转换，不做自由发挥——剧本质量直接决定成片质量，而本地写作不消耗任何积分。

## 2.3 阶段二：平台一键直出（Canvas API）

**为什么全程走 API 而不是 GUI？**

平台的 Web 端登录前有一道 Cap.js 工作量证明验证码（PoW），自动化环境下会被服务端稳定拒绝（连续两次 403）。改用 API Key 后反而获得了三个 GUI 没有的能力：

- 可精确指定全部生产参数（模型、分辨率、时长、风格）
- 可读取官方账单接口，成本数据有据可查
- 可脚本化批处理，便于复现

**生产链路**（全部由平台 API 完成）：

| 步骤 | 接口 | 产出 |
|---|---|---|
| 建项目 | `POST /api/storyboards/quick-start` | 项目 ID |
| 全自动生产 | `POST /api/storyboards/auto-produce` | 剧本 → 资产 → 分镜 → 分集视频 |
| 分镜图生成 | `POST .../scenes/{id}/generate-grid` | 66 张分镜静帧 |
| 视频片段生成 | `auto-produce` 内部流水线 | 36 个视频片段 |
| 成片导出 | `POST .../video-items/export` | 3 集 MP4 |

**关键参数配置**：

```json
{
  "flow_type": "script",           // 直接导入完整剧本，LLM 不自由发挥
  "global_style": "live_ancient",  // 真人古装影视质感
  "aspect_ratio": "16:9",
  "image_model": "bytedance/doubao-seedream-5.0-flash",
  "video_model": "kling-v3",
  "video_resolution": "720p",
  "total_episodes": 3
}
```

**模型选型逻辑**：

| 模型 | 720p 单价 | 多参考图 | 结论 |
|---|---|---|---|
| Kling V3 | 156 积分/秒 | 支持 | **选用** —— 质量与成本的最佳平衡点，且含音轨 |
| Seedance 2.0 | 415 积分/秒 | 支持 9 图 | 一致性更强，但单价 2.7 倍 |
| Seedance 2.0-mini | 65 积分/秒 | 支持 | 成本最低，但人物一致性风险高 |

人物一致性是连续剧的命门。本剧的处理方式是**用分镜静帧锁脸，而非靠视频模型的多参考能力**——先用统一的分镜图定住人物形象，再按图生成视频。这样就能放心选用性价比最高的 Kling V3。

## 2.4 阶段三：素材回收

平台 CDN 上的图片和视频都需要签名才能下载，直接访问返回 403：

```
POST /api/media/sign-urls  {"urls": ["https://canvas-test.ifsdc.com/..."]}
→ 返回临时签名 URL（有效期短，取到即用）
```

素材回收时踩到的三个坑（已写进脚本）：

1. **分镜生成存在项目级锁** —— 同一项目内同时只能跑一个分镜生成任务，并发提交会全部失败。必须串行 + 失败重试。
2. **签名 URL 有时效** —— 取到后立刻下载，不做缓存。
3. **本机代理干扰** —— urllib 默认走系统代理，会导致下载失败。需显式绕过。

## 2.5 阶段四：本地后期（0 积分）

成片下载完成后，**所有修整工作都在本地 ffmpeg 完成，不消耗任何积分**。共处理四项：

### （1）清除资产参考图泄露（28 处）

**问题**：平台生成视频时，部分片段的开头 1–3 秒回落使用了角色资产三视图（白底模型卡），三集共 28 处。

**定位方法**（自动化）：

```python
# 1) 逐帧抽帧（AVAssetImageGenerator，1 秒粗扫 + 0.25 秒精扫）
# 2) 缩至 48px，统计"亮且低饱和"像素占比，阈值 0.35
# 3) 对命中帧做 16×16 灰度 aHash，与角色资产参考图比对，确认泄露的是谁
```

检测结果显示，三集泄露分布为 ep1 十处、ep2 十处、ep3 八处，涉及苏哲、飞流、蒙挚、黎纲、霓凰、太子、誉王、谢氏头目全部 8 个角色。

> 附带一个合规收益：这些资产三视图在面容上明显模仿了原剧演员，清除它们同时降低了肖像权风险。

**修复方法**：将该时间段的画面替换为「泄露结束后第一个干净画面」的缓慢推近（zoompan），并加淡入淡出。**音频轨原样保留，不做任何处理**——因此旁白与对白完全不受影响，叙事流畅性无损。

```bash
[base][cv] overlay=0:0:enable='between(t,13.0,15.2)'
# cv = 静帧 + zoompan 缓推 + fade in/out
```

### （2）人物 / 地点首次出场标注（13 处）

在每个角色、每个地点**第一次出现**时，画面左下角浮现 3.5 秒介绍字条（半透明深底 + 金色竖条 + 宋体主名 + 副题）。

标注时间与剧情精确对位。例如「茶进金陵那天，江左梅郎，也进了城」这句旁白响起时，画面叠的正是「金陵城门 · 大梁帝都」。

| 类型 | 条目 |
|---|---|
| 人物 8 个 | 苏哲·江左梅郎、霓凰郡主、飞流、蒙挚、黎纲、谢氏商行头目、太子、誉王 |
| 地点 5 个 | 滇南古茶山、江边渡口、金陵城门、金陵街市、苏宅 |

### （3）硬字幕烧录

从剧本的旁白 / 对白 beats 生成 SRT，按场景时间轴聚合、按文本长度比例分配时长，用 `subtitles` 滤镜烧录：

```
force_style='FontName=PingFang SC,FontSize=19,PrimaryColour=&H00FFFFFF,
             OutlineColour=&HB4000000,BorderStyle=1,Outline=1.4,Shadow=0.6,MarginV=42'
```

### （4）输出

```bash
-c:v libx264 -preset medium -crf 19 -pix_fmt yuv420p -c:a copy -movflags +faststart
```

音频用 `copy` 直拷，保证音质零损失。

## 2.6 阶段五：轻量预览版

为便于在线播放，另输出 854×480 的压缩版本（单集 < 10 MB），用于仓库 Issue 内嵌播放。

```bash
-vf scale=854:-2 -crf 27 -c:a aac -b:a 96k
```

## 2.7 成本控制的三个原则

| 原则 | 具体做法 | 效果 |
|---|---|---|
| **剧本先行** | 完整剧本一次性灌入，LLM 只做转换不做创作 | 避免生成 — 发现不对 — 重生成的浪费 |
| **只生成一次** | 视频片段生成后无论好坏一律采用，不"抽卡" | 抽卡倍数 1.0，利用率 100% |
| **修正在本地** | 所有画面缺陷用 ffmpeg 修复，绝不为修一帧重生成 | 后期阶段 0 积分 |
